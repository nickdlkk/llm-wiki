# Receiving Code Review

> Source: skills/receiving-code-review/SKILL.md

## 核心工作流

**核心原则：** 技术评估，而非情感表演。验证后再实现，不清晰就提问。

### 6 步响应模式

```
┌──────────────────────────────────────────────────────────┐
│  收到代码审查反馈时的响应模式                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. READ    → 完整阅读反馈，不立即反应                     │
│  2. UNDERSTAND → 用自己的话复述需求（或提问）              │
│  3. VERIFY  → 对照代码库实际验证                          │
│  4. EVALUATE → 技术上是否适合这个代码库？                  │
│  5. RESPOND → 技术性确认或有理有据的反驳                   │
│  6. IMPLEMENT → 逐项实现，每项单独测试                     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 铁律 / HARD-GATE

### 禁止的表演性回应

| ❌ 禁止 | 原因 |
|--------|------|
| "You're absolutely right!" | 明确违反 CLAUDE.md |
| "Great point!" | 表演性认同 |
| "Excellent feedback!" | 表演性认同 |
| "Thanks for catching that!" | 任何感谢表达 |
| "Let me implement that now" | 验证前不行动 |

| ✅ 正确 | 说明 |
|---------|------|
| 复述技术需求 | "Fixed. [描述变更]" |
| 提出澄清问题 | 技术对话 |
| 有理有据反驳 | 用代码/测试证明 |
| 直接行动 | 行动 > 言语 |

**原因：** 行为胜于言语。代码本身展示你听到了反馈。

### 处理不清晰反馈

```
IF 任何项目不清晰:
  STOP - 暂不实现任何内容
  ASK - 请求澄清不清晰的项目

WHY: 项目可能相关，部分理解 = 错误实现
```

**示例：**
```
your human partner: "Fix items 1-6"
你理解 1,2,3,6，不清楚 4,5

❌ 错误: 现在实现 1,2,3,6，之后再问 4,5
✅ 正确: "我理解 1,2,3,6，实现前需要澄清 4 和 5"
```

## 与其他技能的关系

- **requesting-code-review**: 发起审查后接收反馈
- **dispatching-parallel-agents**: 多问题并行调查后统一审查
- **Subagent-Driven Development**: task 完成后的反馈闭环

## 外部 Reviewer 的特殊处理

```
外部反馈 = 待评估的建议，不是必须执行的命令
```

**实现前必查：**

1. 技术上对这个代码库正确吗？
2. 会破坏现有功能吗？
3. 当前实现的原因是什么？
4. 在所有平台/版本上可行吗？
5. reviewer 了解完整上下文吗？

**如果建议有误：** 用技术推理反驳

**如果无法验证：** "没有 [X] 无法验证。是否应该 [调查/询问/继续]？"

**如果与 human partner 的决定冲突：** 先与 human partner 讨论

## Red Flags

| 错误 | 修复 |
|------|------|
| 表演性认同 | 复述需求或直接行动 |
| 不验证就实现 | 先对照代码库验证 |
| 批量不测试 | 逐项实现，每项测试 |
| 假设 reviewer 正确 | 检查是否破坏功能 |
| 回避反驳 | 技术正确性优先于舒适 |
| 部分实现 | 先澄清所有项目 |
| 无法验证却继续 | 说明局限性，请求指示 |

## YAGNI 检查

```
IF reviewer 建议"正确实现专业功能":
  grep 代码库实际使用情况

  IF 未使用: "此端点无人调用。删除（YAGNI）？"
  IF 已使用: 则正确实现
```

## 何时反驳

- 建议破坏现有功能
- Reviewer 缺乏完整上下文
- 违反 YAGNI（未使用功能）
- 技术上不适合此技术栈
- 存在遗留/兼容性原因
- 与 human partner 的架构决策冲突

**反驳方式：** 技术推理，非防御姿态；引用测试/代码；架构问题拉入 human partner。
