# Agent评测漫谈 —— 由浅入深讲解Agent评测（蒸馏）

> **一句话总结**：Agent 评测正在从「答案打分动作」走向「基础设施能力」。核心方法论是三层指标搭桥 + 人人/人机二元化对齐 + 数据飞轮；2026 年长程 Agent + Skill 评测要求基建化（全链路回放 + Case 管理 + 执行沙箱 + AI 评测引擎 + 报告归因 + 回归 + 门禁）。

## 核心命题

**Agent 研发公式**：**观测 + 评测 = 持续迭代**。

文章拒绝三个常见误区：
1. 只看 Agent 最终答案（结果层）
2. 只看离线榜单
3. 一次性设计"复杂精妙"的指标体系

## 一、Agent 评测要回答的根本问题

### 评测对象的演进

| 阶段 | 评测对象 | 核心问题 |
|------|---------|---------|
| 传统机器学习 | 单模型 | "算得准不准" |
| 大模型评测 | 单一模型 | "模型能力强不强" |
| **Agent 评测** | **模型 + 系统 + 工具 + 流程** | "放进真实系统后能不能稳定交付好的结果" |

### 评测四层（结果/过程/效率/风险）

| 层级 | 关注点 | 失败信号 |
|------|--------|---------|
| **结果层** | 任务是否完成，输出是否可用 | 一次性偶然命中 |
| **过程层** | 规划是否合理，步骤是否稳定 | 路径混乱、反复试错 |
| **效率层** | 耗时、Token、工具调用次数 | 路径有解但成本爆炸 |
| **风险层** | 是否越权、是否误操作、是否存在安全隐患 | 越权写入、敏感数据泄露 |

> 两个 Agent 可能最终都"做对了"，但工程价值完全不同。**只看结果会误判同一水平**。

### 观测是评测的基石

Agent 一次执行链路：user_input → 意图识别 → 工具调用 → 状态变更 → 结果输出

> **看不见的问题，几乎不可能被稳定解决。**

工业界发展出 **Trace 系统**：

- 全路径披露黑盒内部逻辑推理
- 记录所有影响模型输出的输入信息
- 解决"我想看 Case 却发现没打日志"的朴素问题

> 对 Agent 的每一个"隐形动作"进行精准观测，是实现从"概率性生成"向"工业级可靠性"跨越的必由之路。

### 小结：Trajectory Evaluation vs Response Evaluation

双重评测 — **既要 Response 也要 Trace**。

## 二、评测的核心方法论

### 2.1 搭桥：跨业务/系统/Agent 三层指标

**搭桥的本质**：模型能力指标和业务结果指标之间有天然鸿沟，必须有中间层。

```
业务层：DAU / 留存 / 点击
系统层：召回率 / 点击率
Agent层：意图识别 / 检索效果 / 结果整合可信度
```

> 只有把这些层次串起来，才能真正回答"为什么业务指标变差"以及"模型能力提升为什么没有带来业务收益"。这件事必须依赖真正懂业务流程的人来共同建立指标体系。

### 2.2 客观 + 主观并行

| 评测类型 | 适用场景 |
|---------|---------|
| **客观评测** | 高频、结构化、可规则化的部分 |
| **主观评测** | 开放性、高价值、复杂业务场景 |
| **主观评测校准** | 校准客观评测和 AI 评测的可信度 |
| **自动化系统** | 规模化 |

### 2.3 人人 / 人机一致方法论

**核心问题**：不同的人评得不一样，机器和人评得也不一样。

**两个一致**：

- **人人一致**：1 个"独裁者"好过 10 个"民主者"。独裁者的作用是拉齐标准 — 避免各团队各自为政。
- **人机一致**：机器评测结果与人工保持一致，否则不置信（规模化意义）。

**对齐的最佳实践（三步）**：

1. **指标下钻** — 把"大而模糊"的概念下钻成多个清晰维度
2. **Rubric 二元化** — 把打分规则尽量收敛成是/否/未知、0/1/unknown
3. **持续迭代** — 用 unknown 占比反查 Rubric 是否合理，直到单条 Rubric 的人人/人机一致率达到 85%/90%

**案例数据**：

- 数字站长应用该方法 → 人机一致率 **99%**
- Beam 改造评测体系 → 人机一致率 **62% → 92%**

> **标注 ≠ 评测**：标注是动作，评测是目标导向的判断流程。机器预标注只有在人机一致率保障时才能称为自动化评测，否则只是机器标注。

### 2.4 数据飞轮：实践科学

**5 个关键环节**：采集 → 清洗 → 评测 → 质检 → 分析/归因（与线上 AB + 持续观测共同构成飞轮）。

**指标体系搭建路径**：

1. 从高频核心场景起步，先定义少量关键指标
2. 从生产环境中收集 Bad Case
3. 沉淀高质量 Good Case，明确什么叫"好"
4. 把 Good/Bad Case 转成标准评测样本
5. 用评测结果反哺 Prompt/Skill/策略/模型优化
6. 再从新的线上表现里持续抽样，形成下一轮迭代

> **Bad Case 价值往往更高** — 暴露能力边界；**Good Case 作用是定义高质量完成的范式**。

**实战数据**：履约数字站长业务项目启动之初 20 个指标，1 年推全后扩展到近 200 个。

### 2.5 专家知识补充模型在垂域的能力不足

- 模型依赖高质量语料 — RLHF/DPO/GRPO 等训练架构简化，但**对高质量核心数据的依赖从未改变**
- 字节豆包 Xpert 众包专家标注平台（地理、代码、法律、医学）
- **破局关键**：引入行业专家知识输入，项目冷启动阶段尤其重要
- **谁来定义"好不好"？靠最懂业务最有 Sense 的行业专家。**

### 2.6 FAQ

| 问题 | 答案 |
|------|------|
| 独裁者必须是 1 个人？ | 团队遵守同一套规范；独裁者负责拍板 + 整合 |
| 独裁者是否有风险？ | 评测体系随业务扩量演进；目标由 BadCase/GoodCase 驱动调整 |
| 冷启动必须设种子评测集？ | **推荐方案**：人工生产少量 + AI 辅助生成/扩写 |
| 专家对"好"的定义不一致？ | **不是噪声，是养分** — 转化为不同风格/策略分支，独立评测 |

## 三、长程 Agent 的观测评测演进

### 短程 vs 长程

| 维度 | 短程 ChatAgent | 长程 Agent |
|------|---------------|-----------|
| 输入输出 | `Query → Answer` | 多步拆解 / 多 Tool / 多 Skill |
| 评测对象 | 回答本身 | 完整任务系统 |
| 案例 | AI 搜索、客服机器人 | Claude Code、Codex、OpenClaw |

**最本质变化**：

> ChatAgent 评测关心"说得好不好"，长程 Agent 评测关心"**事情做成没有，以及是怎么做成的**"。

### Skill 评测 — 2026 年新挑战

**龙虾/Skill 热潮的用户画像（2026 年春节后）**：

- 用户规模从少量专业角色扩展到更广人群
- 商家侧仍在探索，规模有限
- 公司内部 AI at Work 融合（产、运、研、销多角色）
- **Skill 开发门槛越来越低，AI 辅助生成**

**直接结论**：未来需要评测的人 = 每一个会创建、修改、接入 Skill 的人。

**评测系统新要求**：简单 / 标准化 / 自动化 / 接入开发与发布流程。

**本质痛点**：大家不知道怎样写好 Skill，也缺乏 Skill 全生命周期评测工具。

#### 面向 Task 的评测

参考 2026-01-09 Anthropic "AI Agent评估"博客：

- **Task 定义**：具有明确输入和成功标准的单个测试
- **三元组**：`(prompt, expected_behavior, trace)` — 类似短程的 `(query, ground_truth, answer)`
- **多次试验**：模型输出不同运行间有变化，需要多次试验产生更一致结果

### 人评主导走向机评主导

**链路缩短**：

```
短程：核心评测员对齐 → 外包对齐 → 机评对齐
长程：核心评测员对齐 → 机评对齐 → 规模化扩展
```

**原因**：
- 长程 Agent 轨迹更丰富，信息密度高使**人成为卡点**
- Skill 生产门槛低、数量增长极快，人工大规模标注不可持续
- 基座模型能力持续突破

**重新分工**：

- **人工**：高价值标准设计 + Rubric 对齐
- **AI**：规模化运行 + 初筛 + 回归验证
- **平台**：沉淀 + 回放 + 告警 + 归因

> AI 评测真正要放大的，不是"机器打分"本身，而是**核心评测员的判断标准**。

### 长程 Agent 评测基建（7 大能力）

| 能力 | 作用 |
|------|------|
| **全链路回放** | 复现一次任务从输入到结果的全过程 |
| **Case 管理** | 统一维护任务样本、上下文、约束、Rubric |
| **执行沙箱** | 按只读 / 可写 / 高风险分层隔离执行 |
| **AI 评测引擎** | Rubric 驱动的人机对齐 + 自动判分（易用） |
| **报告与归因** | 不仅给分，还要指出问题在规划 / 工具 / 环境 / Skill |
| **回归机制** | 版本升级自动触发历史 Case 回归 |
| **准入准出门禁** | 把评测结果嵌入开发、发布、运营流程 |

> 如果缺少这些能力，评测就容易停留在"单次分析"和"项目制支持"层面，无法真正成为生产系统的一部分。

## 四、总结：评测 = 基础设施能力

**第一，评测对象变了** — 从"回答"到"任务系统"。

**第二，评测方法变了** — 从 `Query → Answer` 文本质量到 `Prompt → Expected Behavior` 行为评测。

> **标准答案不再总是唯一**，过程质量、任务完成度和轨迹质量成为新的核心对象。

### 未来评测体系五大特征

```
看得见问题 · 说得清标准 · 跑得动规模 · 接得上流程 · 带得动迭代
```

### 核心术语对照

| 概念 | 别名 | 定义 |
|------|------|------|
| **任务** | Problem / Test Case | 明确输入和成功标准的单个测试 |
| **试验** | Trial | 每次尝试任务的行动 |
| **评分器** | Grader | 评估 Agent 性能某些方面的逻辑；多个断言（Checks） |
| **记录** | Transcript / Trace / Trajectory | 完整记录：输出、工具调用、推理、中间结果 |
| **结果** | Outcome | 试验结束时环境最终状态 |
| **评估框架** | Evaluation Harness | 端到端运行评估的基础设施 |
| **Agent 框架** | Agent Harness / Scaffold | 使模型作为 Agent 运行的系统 |
| **评估套件** | Evaluation Suite | 测量特定能力/行为的任务集合 |
